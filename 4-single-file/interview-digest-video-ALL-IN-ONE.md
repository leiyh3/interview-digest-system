## 访谈精读视频

把一条长访谈剪成 10 分钟以内的精读视频，发抖音和视频号。成片由三种片段组成：原片片段（说话人原声 + 逐句中文字幕）、讲解段（账号主自己的口播或授权 TTS + 图卡）、纯图卡。流程分两个阶段：先出预览，审片通过后再出成片。

脚本在 `scripts/`，需要 ffmpeg（带 libx264、libass）、Python 3（Pillow、numpy）和一个中文字体（默认 Noto Sans CJK SC）。下载和转写在用户自己的电脑上做。

### 开始前先问清（缺哪项问哪项，一次问完）

1. 素材：源视频文件，加带时间戳的转写（whisper JSON 或 SRT）；用户是否有权剪辑。
2. 平台：默认抖音和视频号，竖版 9:16。
3. 目标时长：默认 10 分钟以内。
4. 账号数据表：抖音、视频号后台导出的视频列表，两个平台分开给。没有就跳过数据分析，D1 填 NA。

看不到的东西（没给的画面、没转写的声音）不假装看过，直接说看不到。

### 流程

**1. 取素材。** 用 `ffprobe` 确认时长、分辨率、有无音轨。把 whisper 的碎片合并成整句：

```
python3 scripts/prep_transcript.py merge whisper.json -o transcript.json
```

剪辑点只能落在整句边界上，所以这一步不能省。脚本会提示哪些句子不是以标点结尾的，抽查开头、结尾和中间各一处，和视频对一对。

**2. 通读并出精剪主线（`storyline.md`），然后停下等用户。** 读完整转写，有视频就抽帧确认谁在说话。主线包含：

- 3 个标题：反转型、数字冲突型、悬念型各一个，公式见 `references/topic_and_title.md`，数字必须出自访谈
- 一句话主张
- 开头 3 秒：第一句话或第一个画面，直接抛冲突、数字或悬念
- 3 到 5 个要点，每个写起止时间码、原话大意、要给观众的判断（这就是讲解段的内容）
- 结尾：一句收束，加一个行动或看下一条的理由；视频号版本要给出转发理由
- 出处表：画面和口播里出现的每个数字、人名、引述，写明时间码；访谈以外的数字写明出处，找不到的标"待核实"
- 预估时长和原片占比（原片累计不超过成片一半，单段原片不超过 60 秒）

用户回复"开始"或给出修改意见后才继续。这是唯一的人工确认点。

**3. 写剪辑计划、翻译、出预览。** 按 `references/edit_plan.md` 写 `plan.json`。只翻译用到的句子：

```
python3 scripts/prep_transcript.py todo transcript.json --plan plan.json -o todo.tsv
## 填 todo.tsv 的 zh 列：人名、数字、单位照原话；不确定的写 [?]，不要猜
python3 scripts/prep_transcript.py apply transcript.json todo.tsv
python3 scripts/cut_video.py plan.json --mode preview --transcript transcript.json --out-dir build
```

讲解段还没录音时，脚本按每秒 4.5 个字估算时长、用静音占位，标为"待配音"。预览是 540×960、低码率。

**4. 技术审片（每次出预览都做）。**

```
python3 scripts/tech_check.py build/preview.mp4 --timeline build/timeline.json --transcript transcript.json --out-dir tech_qa
```

T1 到 T4、T6 的排版部分、T8 由脚本判断；T5、T6 的观感部分、T7 必须对着 `tech_qa/frames/sheet_*.jpg` 逐张看，清单见 `references/tech_review.md`。任何 fail 先修，修完重出预览再审。不是 `cut_video.py` 出的视频用 `scripts/tech_qa.py video.mp4 --out qa/round1`。

**5. 评审循环（技术审片没有 fail 才进入）。**

5a. 有数据表时先跑数据分析，两个平台分开：

```
python3 scripts/analyze_metrics.py douyin.csv --platform 抖音 --out data/douyin_findings.md
python3 scripts/analyze_metrics.py channels.csv --platform 视频号 --out data/channels_findings.md
```

再按 `references/data_analysis.md` 写 `data_insights.md`。样本少于 20 条只当线索，写明样本量。

5b. 两个评审：数据分析师、观众剪辑，提示词在 `references/review_prompts.md`，各按 `assets/rubric.json` 的 12 项打 1 到 5 分。能起子智能体（如 Claude Code 的 Agent 工具）就各起一个，互不通气；不能起时（如网页聊天）按 `review_prompts.md` 的"降级做法"执行，并在交接记录里写明"评审不独立"。

5c. 判定：`python3 scripts/review_gate.py check --round N`。两位都达到 80 分（没有数据时 D1 填 NA，不计入）、没有低于 3 分的项、没有必须修改的问题才通过。不通过就改，每处改动用 `review_gate.py change` 记录，一轮不超过 5 处，重出预览、重审，最多 4 轮。意见冲突时：事实和硬伤 > 前 3 秒和主线 > 节奏 > 其他；拿不准就两种方案都给用户选。

**6. 出成片。** 讲解段换成真实录音（只用用户自己或已授权的声音），翻译补全，然后：

```
python3 scripts/cut_video.py plan.json --mode final --transcript transcript.json --out-dir build_final
python3 scripts/tech_check.py build_final/final.mp4 --timeline build_final/timeline.json --transcript transcript.json --out-dir tech_qa_final
python3 scripts/review_gate.py handoff --tech-report tech_qa_final/tech_report.json
```

成片模式下，"待配音"和缺翻译会被判为 fail。

**7. 交接。** 给用户成片、`HANDOFF.md`（每轮分数、每处改动及来源和理由、采纳和不采纳的建议、仍偏弱的项、发布前要人工确认的事）。技术审片有 fail 时写明"不能发布"。回复里只说结果和一个下一步。

### 边界

- 版权：只用用户有权剪辑的素材；原片少而必要，配上自己的讲解、翻译和判断；每段原片带来源角标，简介里写来源。不整段搬运。
- 事实：画面和口播里的每个数字、人名、引述都能在原访谈里找到并给出时间码，找不到的删掉或标"待核实"。
- 声音：只复刻用户自己或已授权的声音。发布时按抖音、视频号的要求标注 AI 生成内容。
- 评分只说明剪得是否规范，不能保证播放量。

### 文件

- `scripts/prep_transcript.py`：碎片合并成整句；列出要翻译的句子；回填翻译
- `scripts/cut_video.py`：按计划渲染预览或成片：三种片段、三区版式、逐句字幕、来源角标、原片占比检查
- `scripts/tech_check.py`：T1 到 T4、T6 排版、T8 自动检查，其余生成联系表人工看
- `scripts/tech_qa.py`：没有时间线的视频用的独立审片
- `scripts/extract_frames.py`：抽帧和联系表
- `scripts/analyze_metrics.py`：抖音、视频号数据表分析（含转发率）
- `scripts/review_gate.py`：评分表、通过判定、改动记录、交接清单
- `assets/rubric.json`：12 项评分标准、通过线、可填 NA 的项
- `assets/edit_plan.example.json`：剪辑计划示例
- `references/`：剪辑计划格式、技术审片清单、评审提示词、数据分析方法、选题与标题公式
- `templates/metrics_template.csv`：数据表列名模板

# 附录 A：references/edit_plan.md

## 剪辑计划与转写格式

### transcript.json

带时间戳的整句转写，单位秒。用 `prep_transcript.py merge` 从 whisper 输出生成，每项是一句完整的话；`zh` 是中文翻译，`prep_transcript.py apply` 写入。

```json
{"segments": [
  {"id": 0, "start": 0.0, "end": 5.2, "text": "First sentence.", "zh": "第一句话。"},
  {"id": 1, "start": 5.9, "end": 11.4, "text": "Second sentence."}
]}
```

没有 `zh` 的句子会用原文显示字幕，预览时警告，成片时技术审片判 fail。

翻译规则：人名、数字、单位照原话；按意思翻，不照搬语序；一句对一句；不确定的地方写 [?]，不要猜。

### plan.json

| 字段 | 含义 |
|---|---|
| `source` | 源视频路径，相对于 plan.json 所在目录 |
| `aspect` | 只支持 `9:16` |
| `style.title` | 整条视频顶部的标题条，用【】标出要高亮的词 |
| `style.source_label` | 原片片段右上角的来源角标，如"来源：节目名 · 日期" |
| `style.bg` | 背景色（十六进制），或 `blur`（原片模糊背景，上区文字可读性会变差） |
| `style.accent` | 高亮色 |
| `style.bilingual` | `true` 时原片字幕下方加一行小号英文原文 |
| `limits` | `max_source_ratio`（原片占比上限，默认 0.5）、`max_source_clip_sec`（单段原片上限，默认 60）、`max_total_sec`（默认 600） |
| `clips[]` | 按成片顺序排列，可以乱序取材 |

每个片段的字段：

| 字段 | source | narration | card |
|---|---|---|---|
| `id`、`label` | ✓ | ✓ | ✓ |
| `start` / `end` | 源视频起止秒数，自动贴到句子边界 | | |
| `card` | 上区小图卡（最多 2 行） | 中区大图卡 | 中区大图卡 |
| `speaker` | 画面左下的人名身份条 | | |
| `audio` | | 你的口播录音（wav/mp3/m4a） | 可选 |
| `lines` | | 口播稿，逐句成为字幕 | 可选 |
| `duration` | | 没录音时可指定，否则按每秒 4.5 字估算 | 秒数 |
| `source_label` | 覆盖默认角标 | | 引用外部数据时写出处 |

### 版式（9:16，三区）

- 上区：标题条 + 当前片段的小图卡
- 中区：访谈画面（原片片段）或大图卡（讲解、图卡片段）
- 下区：字幕，紧贴画面下方开始。下区下半部分会被平台的标题、简介和按钮盖住，所以不要往下放东西

位置是固定的，所以图卡和字幕不会重叠；文字太长时脚本会缩小字号，缩到下限还放不下，技术审片 T6 判 fail。

### 剪辑原则

- 开头钩子放在最前面，哪怕它在源视频的后半段。
- 每段原片从一句话开头开始，到一句话结尾结束，边界吸附在 0.6 秒以内，超过只提醒。
- 讲解段写"这句话对观众意味着什么"，不复述原话。
- 原片累计不超过成片一半，单段原片不超过 60 秒。超了先删原片，或拆成两段中间加讲解。
- 同一段源视频不在相邻片段里重复使用。
- 成片 10 分钟以内，先删信息密度低的段落。

### 下载和转写（在你自己的电脑上）

```
yt-dlp -f "bv*+ba/b" -o interview.mp4 "<视频链接>"
whisper interview.mp4 --model medium --output_format json
python3 scripts/prep_transcript.py merge interview.json -o transcript.json
```

下载只用于你有权剪辑的视频。英文访谈不要加 `--language zh`，先转写原文，再翻译用到的句子。

# 附录 B：references/tech_review.md

## 技术审片清单

技术审片查有明确对错的硬伤。每次出预览都做，成片前再做一次。先跑 `scripts/tech_check.py`，再看它生成的联系表（每张 12 帧，左上角是时间戳）。

### 脚本自动判断

| 编号 | 检查 | 怎么判断 | 常见修法 |
|---|---|---|---|
| T1 | 黑屏、白屏、纯色帧 | 逐帧计算画面起伏，加 ffmpeg 黑场检测 | 剪辑点是否落在转场或素材缺口上；图卡片段是否忘了写 `card` |
| T2 | 镜头时长 | 场景切换加剪辑点划分镜头，低于 0.8 秒的单独列出 | 有对应语音的短句正常；没有语音的短镜头多半是闪帧，延长或删掉 |
| T3 | 相邻镜头重复素材 | 相邻原片片段的源时间区间，加画面指纹 | 合并重叠区间，或换一段素材 |
| T4 | 剪辑点在句子中间 | 对照整句转写的起止 | 把起止点挪到句子边界，必要时整句取舍 |
| T6（排版） | 图卡和标题有没有进入字幕区、出界、超过行数 | 读 `timeline.json` 里记录的文字框 | 缩短图卡文案 |
| T8 | 原片占比、待配音、缺翻译 | 读 `timeline.json` 的统计 | 预览阶段是警告；成片阶段待配音和缺翻译判 fail |

T2、T3 的画面指纹对固定机位的访谈偏敏感，出现 warn 时看联系表确认，不要直接改。讲解段和图卡片段不参与 T3、T4。

### 必须人工看联系表的项

逐张看联系表，把发现的问题连同时间戳写进 `tech_qa/manual_findings.md`。

**T5 人物标签与画面一致**
- 身份条上的人名，是不是画面里正在说话的人
- 两人对谈时，坐哪边、穿什么、说话的是谁，要和身份条、字幕对得上
- 讲解段提到的人，前后原片里确实出现过

**T6 观感部分**
- 大字和字幕清晰，没有压住人脸
- 同一时刻不超过两层文字（身份条和来源角标不算）

**T7 画面里的数字都有出处**
- 列出画面和字幕里出现的每个数字，写清来自访谈原话（给时间码）、画面里的资料，还是视频以外的来源
- 视频以外的数字，画面或简介里要带出处，找不到出处的删掉
- 数字和单位与原话一致，"倍"和"%"不能互换；翻译时不能把"2 to 3 percent"写成"2 到 3 成"

### 记录格式

```
T7 00:41.0 数字 2%到3%：访谈原话 21:52，通过
T5 01:12.5 身份条写的是主持人，画面是嘉宾：改 speaker 字段，已改
```

# 附录 C：references/review_prompts.md

## 评审提示词

评审团由一个组织者（你自己）和两个评审组成：数据分析师、观众剪辑。

### 隔离规则

两个评审必须互不通气，否则第二个会被第一个的结论带偏。

- 能起子智能体时（如 Claude Code 的 Agent 工具），分别起两个，各自只传下面列出的材料
- 第二个评审的提示词里不能出现第一个评审的分数、意见或文件名
- 评审只写自己的评分文件，不读对方的文件，不读 `review_log.md`
- 只有组织者看得到两份评分，并负责判定和修改

### 不能起子智能体时的降级做法（如网页聊天）

同一个模型、同一段上下文里先后扮演两个角色，第二个必然受第一个影响；而且模型给自己剪的片打分容易偏高。所以：

1. 先完整写完 A 的评分文件，再写 B；B 不引用 A 的分数和措辞。
2. 每个低于 5 分的项都要写出时间码和具体问题；写不出具体问题的项不能打 5 分以下，也不能打 5 分"凑整"。
3. 交接记录里写明"评审不独立，分数仅供参考"。
4. 想要真正独立的评审，把这一步放到 Claude Code 里跑。

### 校准（第一次给一个账号用时做一次）

拿账号已经发过的 3 到 5 条视频，让两个评审按同样标准打分，再和这几条的实际播放、完播、转发排序对比。排序大致一致，分数才有参考价值；不一致就先调整评分标准的措辞或权重，再用于新视频。校准结论写进 `data_insights.md`。

### 给两个评审的共同材料

1. 当前预览视频路径，以及 `tech_qa/frames/sheet_*.jpg` 联系表
2. `storyline.md`（标题、主张、要点、出处表）
3. `assets/rubric.json`（12 项，每项 1 到 5 分，5 分最好；没有数据表时 D1 填 "NA"）
4. 评分文件模板 `reviews/round_N_<角色>.json`
5. `data_insights.md`（如果有）

### 数据分析师

```
你是短视频账号的数据分析师。账号主要发抖音和视频号。你手里有这个账号两个平台的历史数据结论（data_insights.md），
还有一条待发布的预览视频。

请站在"这条视频的数据会怎样"的角度，按 12 项评分标准逐项打 1 到 5 分，并在 notes 里为每个低于 4 分的项写一句
具体、可执行的修改建议，带时间码。
重点看：开头前 3 秒是否符合数据里表现好的开头方式；标题和封面承诺是否兑现；时长是否落在数据里表现好的区间；
有没有值得收藏的结论和关注的理由；抖音和视频号是否分别处理（视频号更依赖转发和社交分发，看有没有让人愿意转给别人的点）。
data_insights.md 里写明样本少、只是假设的结论，按假设对待，不要说成定论。
没有数据表时，D1 填 "NA"，D2、D3 在 notes 里写"无数据，按经验"。

不要去猜另一位评审会怎么打。把分数和意见写进 reviews/round_N_analyst.json。
必须修改才能发布的问题写进 blockers，没有就留空。
```

### 观众剪辑

```
你是这个账号的目标观众，同时是一位剪辑总监。目标观众是对 AI 和科技感兴趣、刷抖音和视频号的普通人，
不一定认识视频里的人物，也不一定听得懂英文。

请先完整看一遍预览视频，再按 12 项评分标准逐项打 1 到 5 分，并在 notes 里为每个低于 4 分的项写一句具体、
可执行的修改建议，带时间码。
作为观众：哪一秒想划走，哪一段没有新信息，字幕和图卡看不看得清，讲解段有没有说出"这对我意味着什么"。
作为剪辑总监：哪段可以删、哪段可以提前，转场是否自然，剪辑有没有改变说话人的原意，字幕翻译有没有偏离原话。

不要去猜另一位评审会怎么打。把分数和意见写进 reviews/round_N_audience.json。
必须修改才能发布的问题写进 blockers，没有就留空。
```

### 组织者怎么用评审结果

1. `python3 scripts/review_gate.py check --round N`
2. 未通过时，先改两位都指出的问题，再改只有一位指出的低分项
3. 分歧在 2 分以上的项，回到视频里自己看一遍再决定，不要取平均
4. 冲突时的优先级：事实和硬伤 > 前 3 秒和主线 > 节奏 > 其他；拿不准就两种方案都给用户选
5. 每处改动用 `review_gate.py change` 记录：对应哪一项、来自谁、为什么改；不采纳的建议也记下来并写原因
6. 一轮改动不超过 5 处，改太多下一轮分数不可比
7. 重出预览，重跑技术审片，再开下一轮

### 如果要省 Token

评审是最贵的环节。校准过、连续两条稳定在 85 分以上之后，把反复出现的问题写进剪辑规则，之后只保留技术审片和一个评审。技术审片成本低，不要省。

# 附录 D：references/data_analysis.md

## 平台数据分析

目标：从账号自己的抖音和视频号后台导出表里，找出播放、收藏、涨粉、转发分别和什么有关，写成 `data_insights.md`，给数据分析师评审当依据。

### 先看数据够不够

- 视频数少于 20 条：只能得出"可能"的假设，每条结论都写上样本量。
- 数据高度集中（少数几条占了大部分互动）：不用平均数，改用中位数，并单独分析那几条为什么特别。
- 抖音和视频号分开分析，不要合并。抖音主要靠推荐流，视频号的分发更依赖转发和社交关系，同一条视频在两边的表现可能完全不同。

### 整理成一张表

两个平台导出表的列名会随版本变化，以你拿到的表头为准。`analyze_metrics.py` 认得常见写法（如"播放量/播放次数""点赞/喜欢""转发/分享"），认不出的必填列会报错并列出它读到的表头，改名或在脚本的 ALIASES 里加别名即可。

整理成：标题、发布时间、时长、播放、点赞、评论、转发、收藏、涨粉，以及平台给出的完播率、平均播放时长、2 秒跳出率等，有就用，没有就空着。

再人工给每条视频补几列特征（填 0/1 或数字）：

- 人物是否熟悉（普通观众是否认识）
- 标题里有没有具体数字、有没有冲突或反转
- 开头钩子类型：悬念、数字、观点、人物
- 讲解段占比（自己讲的时长 / 总时长）

### 四个问题，分别回答

1. **播放由什么决定？** 比较播放排名前 25% 和后 25% 的视频，在人物、标题、发布时间、时长上有什么差别。
2. **收藏由什么决定？** 收藏 / 播放。方法、清单、框架类内容通常收藏率更高，要用自己的数据验证。
3. **涨粉由什么决定？** 涨粉 / 播放。涨粉和播放往往不同步。
4. **转发由什么决定？** 转发 / 播放。视频号重点看这一项：什么样的结论让人愿意转给同事或朋友。

每个问题写：现象、对应的几条视频、你的判断、可信程度（样本量和例外）。

### 输出格式

```
## 数据结论
抖音 N 条，视频号 M 条，统计时间 YYYY-MM-DD。

### 抖音
- 播放：……（依据：视频 A、B、C；可信度：中，样本 N 条）
- 收藏：……
- 涨粉：……

### 视频号
- 播放：……
- 转发：……
- 涨粉：……

### 评分校准（如果做过）
评审给旧视频的分数排序与实际表现排序是否一致：……

### 对下一条视频的建议区间
| 项 | 抖音 | 视频号 | 依据 |
|---|---|---|---|
| 时长 | | | |
| 标题 | | | |
| 开头 | | | |
| 结尾 | | | |
```

建议区间对应评分标准里的 H3、D1、D2、D3。

### 提醒

数据只说明过去哪类内容表现好，不证明因果。一条爆款可能占了绝大部分互动，把它当成规律会误导选题。样本不足时，宁可写"目前看不出规律，需要继续试"。

# 附录 E：references/topic_and_title.md

## 选题与标题公式

### 选题从哪里来

固定 5 到 8 个来源，每周扫一遍：英文播客和访谈（a16z、Y Combinator、Dwarkesh Patel、Lex Fridman、No Priors 等）、大会演讲、公司和 CEO 的博客。

挑素材的三个标准：

1. 说话的人对中文观众是否熟悉
2. 访谈里有没有一句反直觉的话
3. 能不能提炼出一个具体数字或对比

三个都满足的先做。人物陌生但数字很强的，可以做对照实验，别一次做太多。

### 标题公式

精剪主线里固定出 3 个标题：**反转型、数字冲突型、悬念型**各一个。下表其余类型留给以后测试。

`有分量的人` + `反直觉的一句话` + `一个具体数字或对比`

| 类型 | 写法 |
|---|---|
| 反转型 | 【人物】：以前觉得【X】，现在【相反的做法】 |
| 数字冲突型 | 【公司】一分钱不收，凭什么值【金额】？ |
| 预测对赌型 | 【高管】：【大胆预测】，这个赌我接 |
| 翻译成人话型 | 【人物】说了一小时，其实就这【数字】句 |
| 对普通人有用型 | 【专家】教你：用 AI 做【具体场景】的【数字】个方法 |
| 悬念型 | 【事件】，原来是为了这个 |

### 写标题时的检查

- 括号里的内容必须是访谈里真实出现的，不能为了好看编造数字或夸大立场。
- 标题给出的承诺，视频里要兑现。
- 抖音、视频号各定一版标题。视频号的标题和简介要让人愿意转发（"转给做 X 的朋友"这类理由），不要只追求好奇心。
- 封面主标题两行以内，每行 14 字以内，副标题写人物身份或数字。这是经验值，发布前在后台预览里看一眼有没有被裁切。
- 3 个版本里挑最能让陌生观众点开的一个，其余留给另一个平台或下一次测试。

### 封面

用"封面工坊"（`2-cover-studio/cover-studio.html`）生成：两行主标题（第二行高亮色）、副标题、栏目标签、人物照片，可以导出 3:4（1080×1440）或 9:16（1080×1920）。两个平台对封面比例的要求和展示裁切会调整，以发布页的提示为准；主要文字放在画面中部，两种裁切下都不会被切掉。人物照片用有使用权的照片或截图。

# 附录 F：assets/rubric.json（12 项评分标准）

每项 1 到 5 分，5 分最好。通过线：两位评审都不低于 80 分（计分项平均分乘以 20），任何一项不低于 3 分，没有必须修改的问题，最多 4 轮。没有账号数据表时，D1 填 "NA"，不计入总分；总分按其余项的平均分乘以 20 计算。

| 编号 | 名称 | 看什么 |
|---|---|---|
| H1 | 前 3 秒钩子 | 开头 3 秒是否直接抛出冲突、悬念或一个具体数字，而不是自我介绍 |
| H2 | 标题与封面承诺兑现 | 标题和封面承诺的东西，视频里是否清楚给出，而且不夸大 |
| H3 | 点开理由 | 不认识视频里这个人的观众，凭标题和封面有没有点开的理由 |
| C1 | 信息密度 | 每一段是否都有新信息，有没有可以删掉而不影响理解的段落 |
| C2 | 自己的提炼与判断 | 是否有账号主自己的讲解段（口播或图卡）给出拆解、翻译或判断，而不只是原片拼接；讲解是否落在观众关心的“这对我意味着什么” |
| C3 | 事实与出处 | 人名、数字、引述是否和原访谈一致，外部数字是否有出处 |
| R1 | 节奏 | 有没有拖沓的停顿或连续太长的单一画面，换镜频率是否适合竖屏 |
| R2 | 主线连贯 | 从开头到结尾是否一条线讲到底，转场是否自然，是否保留了说话人的完整意思 |
| R3 | 字幕与图卡可读 | 字幕和图卡的位置、字号、停留时间是否足够看清，不遮挡关键画面 |
| D1 | 时长契合数据 | 总时长和分段长度是否贴合这个账号历史数据里表现好的区间；没有数据表时填 NA |
| D2 | 收藏与关注动机 | 结尾或中段有没有给出值得收藏的结论、清单或可用方法，以及关注的理由 |
| D3 | 平台适配 | 封面比例、标题长度、话题标签和简介是否符合平台偏好；抖音和视频号有没有分别处理（视频号更依赖转发和社交分发，标题和结尾要给转发理由） |
